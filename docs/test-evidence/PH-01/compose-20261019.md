# Native Compose acceptance run — 2026-10-19

## Environment

- Docker Engine 28.4.0 and Docker Compose 2.40.3
- Native PostgreSQL 17.6 (`postgres:17.6-bookworm`)
- SeaweedFS 3.96 S3 gateway, pinned by image digest and persisted in the `object-data` Compose volume
- Django/Gunicorn API and Next.js 16.4.2 standalone web server
- System Chromium 154, launched by Playwright with real OPFS, IndexedDB, service worker, and browser offline mode

## Reproduction

```bash
python3 scripts/init-env.py
./scripts/compose.sh up --build -d
./scripts/compose.sh ps
curl --fail --silent http://127.0.0.1:8000/health/ready
./scripts/compose.sh exec -T api python manage.py verify_storage
cd apps/web
RETRO_TEST_BASE_URL=http://127.0.0.1:3000 CHROMIUM_EXECUTABLE=/usr/bin/chromium node tests/smoke.cjs
```

## Result

All four Compose services became healthy. `verify_storage` performed an authenticated S3 upload and a real 1 MiB HTTP Range read, returning `PASS`. The browser run reported:

```text
RESPONSIVE_KEYBOARD_PASS
INSTALLED
NATIVE_SAVE_PASS
OFFLINE_LIBRARY_PASS
OFFLINE_RELOAD_PASS 1
OFFLINE_RELOAD_PASS 2
OFFLINE_RELOAD_PASS 3
OFFLINE_LOAD_PASS
```

The run detected two deployment defects and verified their fixes: Next.js now receives its internal API rewrite target during image build, and local SeaweedFS downloads use the same-origin authenticated range gateway because the gateway rejects unsigned presigned-URL CORS preflights. The gateway validates the manifest ETag before it streams from S3; a regression test covers this precondition.

This evidence covers the HTML5 release and Compose infrastructure only. It does not validate console gameplay, large-file memory limits, the 1 GiB download gate, or physical-device/browser compatibility.
